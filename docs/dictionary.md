# Domain dictionary

This document records the domain's ubiquitous language: business terms and meanings agreed with the project owner and used consistently in conversations, code, tests, APIs, events, and documentation. It guides terminology in the [architecture](architecture.md) and [DDD rules](ddd.md). The terms come from the documented service purpose and from modeling the first use case with the project owner: buying on a trade signal in manual execution mode.

This project is a portfolio and educational simulation: the simulated broker is the only broker, instruments and prices are fictional, and there are no real orders or services for other people. The vocabulary below describes the modeled trading behavior; references to trading, investing, accounts and execution apply to that simulation. A real broker is out of scope. The first iteration uses manual execution mode, and automatic execution mode remains a later goal within the simulation.

Add entries for agreed business concepts. Keep definitions of architectural patterns, DDD modeling concepts, transport protocols, and implementation tools in the relevant technical documentation. For example, Open Host Service (OHS), Published Language (PL), and Anti-corruption layer (ACL) are described in [integration.md](integration.md#2-ddd-relationship).

## Vocabulary

| Term | Meaning in this project |
| --- | --- |
| Analytics application | An external application that owns analytical decision-making and publishes trade signals to Trade Maneuver. Several analytics applications may be connected. Proximtype, a separate non-public application, is only an example: it is not integrated with Trade Maneuver, and any application that implements the contract can take its place. Messaging documentation calls an analytics application a producer; "producer" is not a domain term. |
| Demo analytics application | A fictional stand-in for an analytics application, used to exercise the flow locally without a real analytics application. It publishes trade signals that satisfy the contract, only on fictional instruments and with invented values, and it reads their signal outcomes. It has no analytical model and recommends nothing. Connecting it takes only configuration, as for any analytics application. |
| Trade Maneuver | This microservice. Analytics applications see it as the execution service, which turns their analysis into orders. It also has substantial decision logic of its own: it evaluates trade signals against its domain rules, decides on orders, coordinates their submission to a broker, and exposes their status and outcomes. Use "Trade Maneuver" as its name; "execution service" describes only its role. |
| Trade signal | An analytics application's conclusion about an instrument, such as its direction, confidence, horizon, and validity. A trade signal is neither an order nor a command to execute: Trade Maneuver evaluates it and decides whether, how much, and when to trade. Receipt alone does not establish business validity or successful completion. "Signal" is an acceptable short form in prose. |
| Instrument | A fictional security listed on a specific fictional exchange, identified by its symbol together with the exchange's MIC code. The listing determines the instrument's quote currency. The simulation uses symbols starting with `DEMO_` on the exchange `DEMO`; this code has the MIC format and does not identify a real exchange. |
| Reference price | The instrument price, with its currency and the time it applies to, that an analytics application provides in a trade signal. Trade Maneuver uses it to propose the limit price. |
| Signal validity | The time until which a trade signal may lead to trading. A trade signal is declined if, by then, its order has not been approved in manual execution mode or has not been submitted because no trading session has started; an order still open at the broker is cancelled. Signal validity may span several trading sessions; the analytics application determines it under a rule it owns. It is distinct from the horizon. |
| Horizon | The period, in trading sessions or until a date, over which an analytics application expects the move described by a trade signal to play out. It concerns how long a position is held, not how long a trade signal may lead to an order. |
| Execution | The carrying out of an order at a broker, which the broker confirms as one or more fills, each executing part or all of the order's quantity. Its business effects must not be repeated because of redelivery or retries. |
| Automatic execution mode | The target operating mode within the simulation: trade signal processing and order submission to the broker proceed without human approval. |
| Manual execution mode | An operating mode in which each order awaits an operator's approval before submission to the broker. |
| Broker | The service to which Trade Maneuver submits orders for execution through an API; in this project, the simulated broker. Its integration contract defines how orders are accepted and how outcomes can be confirmed; the broker is the source of truth for whether execution occurred. Do not confuse it with a message broker such as RabbitMQ, which is messaging infrastructure and is always called a "message broker". |
| Simulated broker | The fictional broker, and the only broker Trade Maneuver uses. It imitates order acceptance, fills, rejections, and failures, and it has no connection to a real market, real funds, or a real brokerage account. It does not imitate a specific real broker. |
| Investment configuration | The rules under which Trade Maneuver trades and which trade signals address: what may be traded, the typical order amount, the limit price tolerance, and the amount designated for trading. That amount is a configured limit, not a balance that Trade Maneuver tracks, and it represents no real money. An investment configuration has one currency: its orders are placed only in that currency, through a brokerage account held in it, without currency conversion. Only the analytics applications authorized for an investment configuration may address trade signals to it. It defines rules and limits; it does not hold positions. Always say "investment configuration": "configuration" alone is ambiguous with application configuration, and "account" alone with a brokerage account. "Portfolio" does not name this concept. |
| Brokerage account | A fictional account at the simulated broker, held in one currency, through which Trade Maneuver submits orders under an investment configuration. It holds no real funds and does not correspond to an account at a real broker. Trade signals never reference a brokerage account directly. |
| Position | The quantity of an instrument held in a fictional brokerage account as a result of fills. Trade Maneuver does not track positions in the first use case. |
| Operator | A person who supervises Trade Maneuver, edits investment configurations, and, in manual execution mode, approves or refuses orders awaiting approval. Approval may change the limit price; refusal declines the trade signal. |
| Order | A simulated order to buy or sell a quantity of an instrument at its limit price or better, which Trade Maneuver creates under an investment configuration and submits to a broker. In manual execution mode, an order awaits operator approval before submission. An approved order is submitted only during a trading session. A trade signal leads to at most one order; after an order rejection, order expiry, or order cancellation, trading again requires a new trade signal. |
| Trading | Buying or selling an instrument through orders submitted to the simulated broker. "To trade" always means this simulated activity and never involves a real market, real funds, or a real brokerage account. |
| Trading session | The regular trading hours of an instrument's fictional exchange on a trading day, excluding pre-market and after-hours trading. Trade Maneuver submits orders only during a trading session, and orders execute only within one. |
| Order amount | The money amount that Trade Maneuver allocates to a single order. The order quantity is the largest whole number of units whose cost at the limit price does not exceed it. |
| Limit price | The worst price at which an order may be executed. Trade Maneuver proposes it from the reference price plus a tolerance; an operator approving the order may change it, and the order quantity is then recalculated. |
| Limit price tolerance | The percentage by which a proposed limit price departs from the reference price to allow for price movement; for a buy order, the limit price lies above the reference price. It is part of the investment configuration and the operator can edit it. |
| Order status | The stage of an order's lifecycle. Non-terminal: awaiting approval; approved, waiting for a trading session; submitting, with submission intent recorded but broker acceptance not yet confirmed; open, accepted by the broker and possibly partly filled; and cancelling, with cancellation requested at the broker, at the end of signal validity or by the operator, but final fills not yet confirmed. Terminal: filled, expired, rejected, cancelled, refused by the operator, and lapsed because signal validity ended before submission. An order the broker reports as entirely filled while cancelling ends as filled. Broker acceptance and business completion are distinct. |
| Execution progress | How much of an order's quantity the broker has executed: none, partial, or complete, together with the executed quantity. It is tracked alongside the order status rather than as additional states, and it is reported with an order expiry or order cancellation. |
| Signal outcome | The terminal result of processing one trade signal: exactly one of a signal rejection, a signal decline, an order rejection, an order fill (the order's entire quantity executed, reported as `OrderFilled`), an order expiry, or an order cancellation. A duplicate delivery of a trade signal receives its stored signal outcome under the agreed idempotency contract. A message that reuses a trade signal's identifier with different content is not processed, receives no second signal outcome, and is set aside for manual inspection. A message without a usable identifier, or one that cannot be attributed to a known analytics application, receives no signal outcome because it cannot be correlated or routed; it is set aside for manual inspection. |
| Business rejection | A refusal to perform a requested action because it violates a domain rule or precondition. A terminal rejection retains its outcome for duplicate handling. A signal decline is the business rejection of a trade signal; a signal rejection is a contract violation, not a business rejection. |
| Signal rejection | Trade Maneuver's refusal to act on a message that does not satisfy the trade signal contract or contradicts itself, for example a malformed message, a missing required field, a reference to an unknown investment configuration, an analytics application not authorized for the investment configuration, or a reference price in a currency other than the instrument's quote currency. Some violations are detected only when Trade Maneuver resolves the instrument at the broker. A rejected message never leads to an order. It is reported as `SignalRejected`. |
| Signal decline | Trade Maneuver's decision not to trade on a valid trade signal, for example because the signal expired before evaluation, the instrument is quoted in a currency other than the investment configuration's, trading would violate a limit, or an operator refused the order. It is reported as `SignalDeclined` with a reason from a fixed list; an operator's note on a refusal stays in Trade Maneuver's audit trail and is not reported. |
| Order rejection | A broker's refusal to accept an order submitted by Trade Maneuver. It is reported as `OrderRejected`. |
| Order expiry | The end of an order whose trade signal's validity ends before the order is completely filled: Trade Maneuver cancels the remainder at the broker. It is reported as `OrderExpired` with the filled quantity, which may be zero. |
| Order cancellation | The end of an order cancelled before its signal validity ends, either by the operator in Trade Maneuver while the order is approved or open, or outside Trade Maneuver by the broker. It is reported as `OrderCancelled` with the filled quantity, which may be zero. |
| Recoverable failure | A processing failure for which the workflow defines a retry or recovery path. An uncertain external outcome must be reconciled before an irreversible action is retried. |
| Money | An exact amount together with its currency. Amounts are invented and represent no real money, even though currencies use real codes such as EUR. Precision, scale, and rounding rules are explicit; calculations and representations must not pass through `float`. |

## Using and extending the dictionary

- Use these terms consistently in conversations, code, tests, APIs, events, and documentation. Translate external vocabulary at integration boundaries when its meaning differs.
- Add or revise entries when an agreed business concept is introduced or clarified. Keep definitions consistent with the architecture, DDD rules, and accepted ADRs.
- When a concept could be taken for something real, state in its own entry that it is fictional. Other entries rely on that statement and need not repeat it.
- Resolve ambiguous meanings with the project owner. Illustrative examples in other documents, such as reservation limits, do not establish business rules. Further use cases, such as exiting positions, will extend these terms.
