# TM-003: Investment configuration created by a console command

## Goal

At deployment, the project owner creates the single investment configuration through a console command. Trade Maneuver persists it with its rules and records the creation in the audit trail.

## Scope

In scope:

- An ADR with the next free number and `Status: Proposed` for Money and exact arithmetic with `brick/money` and `brick/math`. It defines precision, scale, rounding modes and rounding boundaries per operation, and the persistence and serialization representation (PostgreSQL exact numeric types, decimal strings, never `float`).
- Adding `brick/money` and `brick/math`.
- The registry of known analytics applications in the Trading context configuration, supplied from the environment at deployment. In this task each entry has the analytics application identifier, which producers send as `source`. Later tasks add fields to the entries.
- The `InvestmentConfiguration` aggregate, its repository, persistence model and migration, and the console command that creates it.
- A custom PHPStan rule that allows calls to an aggregate's `state()` only in repository implementations and tests.
- An append-only audit trail and the transaction manager port with its Laravel implementation, for use by this and later tasks.

Out of scope:

- Editing in the GUI (TM-013).
- More than one investment configuration, creating one in the GUI, the amount designated for trading, and a rule for what may be traded.
- Verifying the brokerage account at the broker.

## Requirements

The investment configuration holds:

- An identity, plus the reference that trade signals use as `investmentConfigurationRef`. The reference is given as a command argument, is non-empty, and is unique.
- A currency: EUR in this iteration. It cannot change after creation.
- A brokerage account: a fictional account identifier at the simulated broker, held in the investment configuration's currency. It cannot change after creation.
- An order amount: Money greater than zero, in the investment configuration's currency.
- A limit price tolerance: an exact decimal percentage from 0 % to 5 % inclusive.
- Authorized analytics applications: a set of identifiers from the registry. The set may be empty, in which case every trade signal addressing this investment configuration is rejected.

Behavior:

- The command creates the investment configuration and one audit record in one transaction. The audit record holds the actor (the console command), the time from the clock, the entity, and the created values.
- The command refuses to run when an investment configuration already exists. This iteration has exactly one.
- Invalid input is refused before any side effect, with a clear error message.
- The aggregate exposes `id()` and an immutable `state()` for repository mapping ([ADR-0001](../ADR/adr-0001-domain-independence-from-eloquent.md), [ADR-0002](../ADR/adr-0002-aggregate-state-for-eloquent-persistence.md)). Reconstitution emits no domain events.

## Decisions

- Money library: `brick/money` with `brick/math`, selected by the owner on 2026-10-31. Approving this task approves adding these dependencies.
- The registry of analytics applications is deployment-time configuration and is not edited in the GUI (owner decision, 2026-10-31).
- The command refuses a second investment configuration (owner decision, 2026-10-31).
- A custom PHPStan rule enforces the persistence-only use of `state()` that [ADR-0002](../ADR/adr-0002-aggregate-state-for-eloquent-persistence.md) requires (owner decision, 2026-11-02). Approving this task approves adding the rule to `phpstan.neon.dist`.

## Constraints

- Verify that the installed versions of `brick/money` and `brick/math` support PHP 8.5 before relying on their APIs.
- Deptrac allows the Money library in `Domain` and still forbids framework dependencies there.
- The audit trail is append-only and is committed on the same connection and in the same transaction as the aggregate.
- The PHPStan rule covers every aggregate without per-aggregate configuration and adds no dependency.

## Acceptance criteria

- [ ] Console command feature test: with valid input, the command creates exactly one investment configuration with the given reference, EUR, brokerage account, order amount, tolerance, and authorized analytics applications, plus one audit record in the same transaction.
- [ ] Console command feature test: a second run is refused and changes nothing.
- [ ] Console command feature test: each invalid input is refused without side effects: an order amount of zero or less, or in another currency; a tolerance below 0 % or above 5 %; a currency other than EUR; an empty or duplicate reference; an analytics application that is not in the registry.
- [ ] Domain unit tests without Laravel or a database cover the tolerance bounds (0 % and 5 % accepted, values just outside rejected), order amount validation, immutability of state DTOs and value objects, and reconstitution without domain events.
- [ ] A PostgreSQL mapping test shows a round trip that preserves exact amounts and the authorized set, with no conversion through `float`.
- [ ] A PostgreSQL test shows that a failing audit write rolls back the investment configuration.
- [ ] The Money ADR exists with `Status: Proposed`.
- [ ] A PHPStan rule test shows that a call to `state()` outside a repository implementation or test is reported, and that calls in those places are accepted.
- [ ] Architecture and DDD statements about how `state()` is consumed match the enforced rule.
- [ ] `CI_WITH_MUTATION=diff make ci` passes, and Infection covers the new domain code with no unexplained surviving mutants.
