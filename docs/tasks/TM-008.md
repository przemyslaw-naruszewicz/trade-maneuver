# TM-008: Instrument checks at the simulated broker

## Goal

Evaluation continues with instrument checks against the simulated broker in the local application, with no real broker, real orders, or real money:

- A trade signal for an instrument that is unknown, unavailable, or quoted in a currency other than the investment configuration's ends with `SignalDeclined` and a reason code.
- A reference price in a currency other than the instrument's quote currency ends with `SignalRejected`.

Later tasks add the other broker operations to this adapter as they introduce them.

## Scope

In scope:

- The instrument check step of the evaluation orchestrator.
- The broker gateway port with its instrument lookup operation, and a deterministic fake used only in tests.
- An infrastructure adapter for the port: the simulated broker, with a catalogue of fictional instruments.
- Binding the port to the simulated broker in the Trading service provider.
- Port tests shared with the test fake.
- Documentation of the local run up to evaluation.

Out of scope:

- Order creation and `OrderAmountTooSmall` (TM-009).
- Order submission, broker events, the simulated broker's state in PostgreSQL, and scripted behaviors (TM-014).
- Broker rejection and partial fills (TM-015).
- The trading session calendar (TM-016).
- Cancellation (TM-017), status queries (TM-018), and external cancellations (TM-019).
- A real broker adapter in any form: no code, configuration, or instructions for a real broker or a live brokerage account.
- Real instruments and real market data.
- Network calls and the separate service (TM-020).
- Connecting Proximtype.
- More than one broker, and broker selection logic.
- CD and VPS deployment.

## Requirements

### Instrument lookup

- The broker gateway port looks up an instrument by symbol and MIC and returns its availability and quote currency.
- A lookup failure (timeout, broker unreachable) is a recoverable failure, not a decline. Evaluation is retried later.

### Order of checks

Contract rejections already happen at intake (TM-004), and `SignalExpired` and `UnsupportedDirection` come first (TM-007). Evaluation then checks, in this order:

1. `InstrumentUnavailable`, when the instrument is unknown or unavailable at the broker;
2. `SignalRejected`, when `referencePrice.currency` differs from the instrument's quote currency (violation on `referencePrice.currency`);
3. `UnsupportedCurrency`, when the quote currency differs from the investment configuration's currency.

A trade signal that passes all checks is left ready for order creation (TM-009).

### Rules

- Evaluation uses the investment configuration as it is at evaluation time.
- Signal outcomes are recorded in the outbox in the evaluation transaction, using the outcome message schema from TM-004.

### Adapter

- The adapter lives in the Trading `Infrastructure` layer, behind the broker gateway port. Its types and identifiers never reach `Domain` or `Application`.
- It reads only its catalogue and runs no queries on Trading tables, so that it can move to a separate service (TM-020).

### Catalogue

- The catalogue is configuration. Each entry has a symbol, an exchange, a quote currency, and availability.
- Every symbol starts with `DEMO_`. The exchange is the fictional code `DEMO`, which was not in the ISO 10383 registry on 2026-11-02.
- The simulated broker holds no market prices and uses no market data.
- A symbol outside the catalogue is unknown to the simulated broker.

The catalogue below is proposed in this draft; the owner confirms it when approving. TM-015, TM-017, TM-018, and TM-019 add further instruments.

| Symbol | Quote currency | Availability | Result of evaluation |
| --- | --- | --- | --- |
| `DEMO_A` | EUR | Available | Passes all checks |
| `DEMO_G` | USD | Available | `SignalDeclined` with `UnsupportedCurrency` for a reference price in USD |
| `DEMO_H` | EUR | Unavailable | `SignalDeclined` with `InstrumentUnavailable` |

### Binding

- The Trading service provider binds the broker gateway port to the simulated broker. Only tests bind the deterministic fake.
- There is no configuration for choosing an adapter while the simulated broker is the only one outside tests.

### Naming

- Code, configuration, logs, and documentation call it the simulated broker. It has no brand name and imitates no real broker's name or API ([dictionary](../dictionary.md)).

### Documentation

- README describes the simulated broker and how to reproduce each result in the catalogue with the demo analytics application (TM-006).
- [integration.md](../integration.md) states that `DEMO` has the MIC format but is a fictional code, not a registered MIC.
- The documentation describes the broker as simulated. It makes no promise of profit, shows no performance or effectiveness results, gives no instructions for a live brokerage account, and does not call the project production-ready or safe.

## Decisions

- The owner approved the order of checks on 2026-10-31.

The owner made these decisions:

- The simulated broker starts as an adapter inside the application. A separate service follows once the basic flow works (TM-020).
- The adapter arrives together with the broker gateway port and grows with the tasks that add broker operations, so that each stage of the flow can be shown without a fake.
- The deterministic fake stays in the test suite for scripted scenarios, and both pass the same port tests.
- The catalogue holds only fictional instruments on a fictional exchange, with no market prices and no brand name.

## Constraints

- No new dependencies.
- Only the broker gateway is substituted in application tests, and the time is fixed through the existing clock binding (TM-007). PostgreSQL, repositories, inbox, outbox, and audit are real.
- Adapter tests stay at the adapter's own boundary. Business rules are covered by the Behat scenarios and application tests ([testing-strategy.md](../testing-strategy.md#test-pyramid)).

## Acceptance criteria

- [ ] Behat: each of `InstrumentUnavailable` and `UnsupportedCurrency` ends with one `SignalDeclined` outbox entry carrying that reason.
- [ ] Behat: a reference price currency different from the instrument's quote currency ends with `SignalRejected`.
- [ ] Behat: the order of checks holds: a `short` trade signal for an unavailable instrument is declined with `UnsupportedDirection`.
- [ ] PHPUnit application test: a lookup timeout writes no outcome, and evaluation succeeds on retry.
- [ ] Domain unit tests cover the decline transitions and the reason codes.
- [ ] Shared port tests pass for both the test fake and this adapter: lookup of an available, an unavailable, and an unknown instrument.
- [ ] Adapter test: the shipped catalogue contains only `DEMO_` symbols and the exchange `DEMO`.
- [ ] PHPUnit integration test: outside the test bindings, the container resolves the broker gateway port to the simulated broker.
- [ ] A manual check in the local environment is described in the PR. The demo analytics application publishes trade signals through RabbitMQ, and:
  1. `DEMO_G` with a reference price in USD ends with `SignalDeclined` and `UnsupportedCurrency` in its outcome queue;
  2. `DEMO_H` and a symbol outside the catalogue end with `SignalDeclined` and `InstrumentUnavailable` in its outcome queue;
  3. `DEMO_A` passes evaluation and has no signal outcome.
- [ ] README and [integration.md](../integration.md) contain the documentation listed above and follow its rules.
- [ ] `CI_WITH_MUTATION=diff make ci` passes.
