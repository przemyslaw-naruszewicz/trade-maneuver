# TM-007: Trade signal evaluation: expiry and direction

## Goal

Each accepted trade signal is evaluated in its own transaction after intake. An expired trade signal or a `short` one ends with `SignalDeclined` and a reason code. These checks need no broker, so they run in the local application.

## Scope

In scope:

- The evaluation step of an explicit orchestrator, triggered after intake commits.
- The `SignalExpired` and `UnsupportedDirection` declines.

Out of scope:

- The broker gateway, instrument lookup, and the declines and the rejection that depend on it (TM-008).
- Order creation and `OrderAmountTooSmall` (TM-009).

## Requirements

### Triggering and recovery

- Evaluation runs through the PostgreSQL-backed job queue after the intake commit.
- It is recoverable: an accepted but unevaluated trade signal is evaluated after a worker crash or restart.
- Each trade signal reaches at most one evaluation decision, even if the job runs more than once.

### Order of checks

Contract rejections already happen at intake (TM-004). Evaluation then checks, in this order:

1. `SignalExpired`, when now ≥ `validUntil`.
2. `UnsupportedDirection`, for a `short` trade signal.

A trade signal that passes both checks has no signal outcome and waits for the instrument checks (TM-008).

### Rules

- `confidence`, `horizon`, and `expectedMove` do not influence decisions. Trade Maneuver does not judge the age of `referencePrice.asOf`.
- Signal outcomes are recorded in the outbox in the evaluation transaction, using the outcome message schema from TM-004.

## Decisions

- The owner approved the order of checks on 2026-10-31. TM-008 continues it.
- Every trade signal is independent: there is no position tracking.

## Constraints

- Evaluation reads the time through the existing PSR-20 clock binding. Tests fix the time on that binding, for example with `travelTo()`, and add no clock port or fake. Nothing else is substituted in application tests: PostgreSQL, repositories, inbox, outbox, and audit are real.
- Tests that exercise queue or worker guarantees use the database queue driver, not `sync` ([testing-strategy.md](../testing-strategy.md#real-infrastructure-and-failure-testing)).

## Acceptance criteria

- [ ] Behat: each of `UnsupportedDirection` and `SignalExpired` ends with one `SignalDeclined` outbox entry carrying that reason.
- [ ] Behat: the order of checks holds: an expired `short` trade signal is declined with `SignalExpired`.
- [ ] Behat: a `long` trade signal inside its validity has no signal outcome after these checks.
- [ ] PHPUnit application test: a trade signal accepted before a worker crash is evaluated after restart, and running the evaluation job twice produces one outcome.
- [ ] Domain unit tests cover the decline transitions, the reason codes, and the expiry boundary (now = `validUntil` is expired).
- [ ] A manual check in the local environment is described in the PR: the demo analytics application (TM-006) publishes a `short` trade signal and one whose validity has ended, and each ends with `SignalDeclined` and its reason in the outcome queue.
- [ ] `CI_WITH_MUTATION=diff make ci` passes.

## Dependencies

- Blocked by: TM-004, TM-006.
- Unblocks: TM-008, TM-009.

## Verification

- Behat scenarios and PHPUnit application tests at the Trading application boundary, with the time fixed through the existing clock binding.
- The manual check described in the PR.
- `CI_WITH_MUTATION=diff make ci`.
