# TM-004: Trade signal intake and signal rejection

## Goal

A `tm.trade-signal.v1` message passed to the Trading application boundary is durably accepted exactly once. A message that violates the contract ends with a stored `SignalRejected` signal outcome in the outbox. Redeliveries never repeat processing.

## Scope

In scope:

- The intake use case at the application boundary. Its input is the raw message body plus the authenticated publisher identity: the RabbitMQ user taken from the AMQP `user_id` property. The transport adapter (TM-005) supplies these; tests supply them directly.
- The inbox, the `TradeSignal` aggregate with its repository and persistence, the transactional outbox, and the signal outcome integration event.
- The outcome message schema, documented in [integration.md](../integration.md).
- Registry entries of known analytics applications, extended with the RabbitMQ user each one publishes as.
- Behat Trading contexts that call application commands rather than HTTP.

Out of scope:

- RabbitMQ consumption and publication (TM-005).
- Evaluation, declines, and the reference price currency check (TM-007, TM-008).

## Requirements

### Acceptance

- One transaction on one connection commits: the inbox entry (unique per consumer and message `id`), the trade signal, the audit record and, for a rejection, the signal outcome in the outbox. A failure rolls back all of them.
- A valid trade signal is stored as received and waits for evaluation (TM-007). No evaluation outcome exists at commit.

### Contract validation

Validate structure and values per [integration.md §3](../integration.md#3-contract-tmtrade-signalv1):

- `id`: UUID.
- `type`: exactly `tm.trade-signal.v1`.
- `time`, `validUntil`, `referencePrice.asOf`: ISO 8601 in UTC.
- `instrument.symbol`: required. `instrument.mic`: the ISO 10383 MIC format, four uppercase alphanumeric characters. Only the format is checked, with no registry lookup, so the simulated broker's fictional exchange code `DEMO` (TM-008) passes. An instrument the broker does not know is declined at evaluation with `InstrumentUnavailable` (TM-008).
- `direction`: `long` or `short`.
- `confidence`: a decimal string from 0 to 1.
- Horizon: at least one of `horizon.sessions` (a positive integer) or `horizon.at` (a date).
- `expectedMove.min` and `.max`: optional, because their optionality is still open. When present, both are decimal percentage strings and `min ≤ max`.
- `referencePrice.amount`: a decimal string greater than zero. `referencePrice.currency`: an ISO 4217 code.
- `extensions`: optional, not interpreted.
- Decimal values are never converted through `float`.

### Signal outcomes

`SignalRejected` covers:

- an invalid v1 message, a missing required field, or an invalid value;
- an unknown `investmentConfigurationRef`;
- an analytics application not authorized for the investment configuration.

The outcome lists the violations: a field path and a message for each.

These messages receive no signal outcome. The use case returns a distinct "not processable" result, which the transport maps to dead-lettering:

- a body that cannot be parsed, or no valid `id`;
- a missing `source`, or a `source` that is not a known analytics application;
- a missing publisher identity, or one that is not the RabbitMQ user registered for the `source`;
- a message that reuses an `id` with different content (see Duplicates).

Each of them is logged and audited with the message metadata.

### Duplicates

- Same `id` and same content: no new processing. If a signal outcome is stored, the same outcome message (same message identity) is recorded in the outbox again for republication. The duplicate is audited.
- Same `id` with different content: not processed, no outcome, audited as a conflict, logged as a warning, and returned as "not processable". Content is compared through a stored fingerprint of the message body.

### Outcome message schema

The draft proposes this schema; the owner confirms it when approving the task. It is CloudEvents-inspired, like the intake contract:

- `id`: the outcome message's UUID, stable across republication;
- `source`: `trade-maneuver`;
- `type`: `tm.signal-outcome.v1`;
- `time`: ISO 8601 in UTC;
- `signalId`: the trade signal's `id`;
- `outcome`: `SignalRejected`, `SignalDeclined`, `OrderRejected`, `OrderFilled`, `OrderExpired`, or `OrderCancelled`;
- `reason`: the decline reason code, only for `SignalDeclined`;
- `executedQuantity`: an integer number of whole units, for `OrderFilled`, `OrderExpired`, and `OrderCancelled`;
- `violations`: a list of `{field, message}`, only for `SignalRejected`.

## Decisions

The owner made these decisions:

- Messages without a valid `id`, from an unknown `source`, or whose `source` does not belong to the publishing RabbitMQ user receive no outcome and are dead-lettered.
- A conflicting duplicate gets no second outcome.
- `source` must match the RabbitMQ user given by AMQP `user_id`. The registry maps each analytics application to its RabbitMQ user.

The owner decided that `instrument.mic` is checked by format only, so that fictional instruments can use a fictional exchange code, and that a conflicting duplicate is dead-lettered.

## Constraints

- Uniqueness of the inbox entry and of the trade signal `id` is enforced in PostgreSQL. A lookup before insert is not enough.
- No RabbitMQ or framework types in `Domain` or `Application`.
- Follow [architecture.md](../architecture.md#idempotency-and-reliable-messaging) for inbox, outbox, and atomicity.

## Acceptance criteria

- [ ] Behat: each signal rejection case (invalid structure, missing field, invalid value, unknown investment configuration, unauthorized analytics application) ends with one `SignalRejected` outbox entry listing the violations.
- [ ] Behat: a duplicate delivery of a rejected trade signal records the stored outcome again, with the same message identity, and processes nothing new.
- [ ] Behat: a valid trade signal is stored and awaits evaluation, with no outcome.
- [ ] Behat: a trade signal with the exchange code `DEMO` passes contract validation, and one whose `instrument.mic` does not have the MIC format ends with `SignalRejected`.
- [ ] Behat or PHPUnit application test: the conflicting duplicate, missing `id`, unknown `source`, and `source` and publisher mismatch cases return "not processable", write no outcome, and are audited.
- [ ] PostgreSQL test with independent connections: concurrent delivery of the same `id` creates one inbox entry, one trade signal, and at most one outcome.
- [ ] PostgreSQL test: a failure in the outbox write rolls back the inbox entry, trade signal, and audit record.
- [ ] Domain unit tests cover the trade signal's rejection behavior, the immutability of state DTOs, and reconstitution without domain events.
- [ ] [integration.md](../integration.md) documents the outcome message schema.
- [ ] `CI_WITH_MUTATION=diff make ci` passes.
