# TM-011: Orders screen

## Goal

The logged-in operator sees everything needed to decide on each order awaiting approval. The start page and the panel navigation show how many orders await approval.

## Scope

In scope:

- A Livewire orders screen in the protected panel from TM-010, reading through the read model from TM-009 ([ADR-0004](../ADR/adr-0004-livewire-eloquent-read-models.md)).
- The content of the start page from TM-010, and a count of orders awaiting approval in the panel navigation.
- Automatic updates of the orders screen, the start page, and the count, without a page reload.
- Browser tests of these screens ([testing strategy](../testing-strategy.md#browser-tests-with-playwright)), with a seeder for their data.
- The instruments `DEMO_B` and `DEMO_C` in the simulated broker's catalogue.

Out of scope:

- Approve, refuse, and cancel actions (TM-012, TM-019), including how updates behave while their forms and confirmations are open.
- Orders in other statuses, which TM-012 adds to the orders screen and the start page.
- Notifications.
- Profit, performance, or effectiveness figures. The screen shows only order status and execution progress (owner decision).

## Requirements

### Orders awaiting approval

The screen lists these orders, sorted by `validUntil` with the soonest first. Each shows:

- for the trade signal: instrument (symbol and MIC), direction, confidence, horizon, expected move, reference price with currency and `asOf`, `validUntil`, and the analytics application;
- for the order: order amount, limit price, quantity, and status.

### Automatic updates

- The screen updates itself every 30 seconds through Livewire polling, without a page reload. This adds no new service or dependency.
- An update replaces only what changed and keeps the scroll position and focus.
- The screen shows the time of the last successful update.
- Each order awaiting approval shows the time left until `validUntil`. The browser counts it down between updates.
- An order added or changed by an update stays marked for about 10 seconds.
- When updates fail, a message says that the connection is lost and that statuses and the time left may be out of date. The screen keeps trying, offers an immediate retry, and clears the message after a successful update.

### Start page and panel navigation

- The start page shows the number of orders awaiting approval with a link to the orders screen, and the soonest `validUntil` with its instrument and time left. With no order awaiting approval, it says so.
- The panel navigation gets an Orders entry, which links to the orders screen and shows the number of orders awaiting approval on every panel page. It follows the mockup's order: after Start, and before Investment configuration when that entry exists.
- Both update themselves at the same interval as the orders screen. An update of the count leaves the rest of the page as it is, including a form being edited.

### Display

- Money and decimal values are formatted exactly, without `float`. Output is escaped.
- The orders screen follows [`orders.html`](../gui-design/orders.html) and the start page follows [`start.html`](../gui-design/start.html), built from the design system of TM-010 in both themes. The lost connection message, the retry, the marked order, and the empty state follow the [Live updates](../gui-design/foundations.html#live-updates) and [Screen states](../gui-design/foundations.html#screen-states) sections of `foundations.html`. Elements that the mockup shows but this task does not require are not built.
- The component reads only through read models, never loads aggregates for display, and keeps no read model in a public property ([architecture.md](../architecture.md#cqrs), [ADR-0004](../ADR/adr-0004-livewire-eloquent-read-models.md)).

### Browser tests

- The seeder lives in `src/Trading/Infrastructure/`, and `bin/e2e` runs it after `BrowserTestOperatorSeeder`. Through the application's use cases, it creates the investment configuration `demo-eur` with the brokerage account `DEMO-ACC-001`, an order amount of 200.00 EUR, a limit price tolerance of 0.50 %, and the authorized analytics application `demo-analytics`. When TM-013 is on `main`, this task extends its seeder, which already creates that investment configuration. From long trade signals of `demo-analytics`, it then creates the three orders awaiting approval that `orders.html` shows, with the mockup's values: `DEMO_A` at a reference price of 10.40 EUR (limit price 10.45 EUR, quantity 19), with a confidence of 0.72, a horizon of 5 trading sessions, and an expected move of +2.00 % to +4.00 %; `DEMO_B` at 6.20 EUR (6.23 EUR, 32); and `DEMO_C` at 24.80 EUR (24.92 EUR, 8), without an expected move. Their `asOf` is the time of seeding, and their `validUntil` lies after the end of the run, in the mockup's order. The registry of the e2e application knows `demo-analytics`, set through `TRADING_ANALYTICS_APPLICATIONS` on `e2e-app` in `compose.yaml`.
- The simulated broker's catalogue (TM-008) holds `DEMO_A` but not `DEMO_B` or `DEMO_C`. This task adds both to the shipped catalogue, quoted in EUR and available, so they pass the instrument checks as `DEMO_A` does.
- The mockup comparisons use `expectToMatchMockup` element by element, because the mockup pages also show elements of later tasks and times of their own. They cover every element this task requires whose content does not depend on the time of the run, as the acceptance criteria list them. The time left, `validUntil`, `asOf`, the last update time, and the start page's soonest `validUntil` depend on it, so feature tests and behavior assertions check them instead.
- The tests drive the updates with Playwright's clock, so they need not wait 30 seconds, and make the update requests fail with Playwright's request routing instead of stopping `nginx`.

## Decisions

- The owner decided on 2026-11-03 that the orders screen updates itself without a page reload and does not disturb an operator who is deciding. The owner expects little traffic, so updates need not be frequent. The 30-second interval and the 10-second marking are proposed in this draft; the owner confirms them when approving.
- The start page and the panel navigation show and update the number of orders awaiting approval (owner decision, 2026-11-03), so the operator learns of a new order on any panel page.
- The look of the screens and their behavior in the browser are checked by this task's browser tests, not by manual checks ([testing strategy](../testing-strategy.md#browser-tests-with-playwright)). Manual checks keep only what the seeded data cannot show: an order from a new trade signal during the run, its marking, and the empty state. The seeder runs before the tests, its orders rule out the empty state, and the Playwright service cannot reach the application's use cases or Docker. This is proposed in this change; the owner confirms it when approving.
- `DEMO_B` and `DEMO_C` go into the shipped catalogue of the simulated broker, not into a catalogue only for the e2e application (owner decision, 2026-11-25). The seeded orders then use the mockup's instruments, and the development environment can reproduce them with the demo analytics application.

## Constraints

- Keep the component thin: it handles presentation and reads through read models.
- Check the polling behavior of the installed Livewire version before relying on it, and check that Playwright's clock drives it.
- A change to `bin/e2e` or `compose.yaml` follows [SDLC §6](../../SDLC.md#changes-to-ci-configuration).

## Risks

- The browser tests create no order during a run, so an update that brings a new order, its marking, and the empty state are checked only by feature tests and manual checks.

## Acceptance criteria

- [ ] Feature test: an authenticated operator sees an order awaiting approval with every listed trade signal and order field, including the reference price `asOf`.
- [ ] Feature test: orders awaiting approval are sorted by `validUntil`, soonest first.
- [ ] Feature test: an unauthenticated request, or one with password only, cannot see the screen.
- [ ] Feature test: decimal values are displayed exactly, using a value whose rendering through `float` would be wrong.
- [ ] Feature test: the rendered orders screen, start page, and navigation count each poll every 30 seconds.
- [ ] Feature test: the start page shows the number of orders awaiting approval, and the soonest `validUntil` with its instrument, and it says so when no order awaits approval.
- [ ] Feature test: the panel navigation contains the Orders entry after Start and before Investment configuration when that entry exists; it links to the orders screen and shows the number of orders awaiting approval, and the next render after a new order shows the new number.
- [ ] Feature test: after a new order is created, the next render of the orders screen shows it and a new last update time.
- [ ] Adapter test: the shipped catalogue of the simulated broker lists `DEMO_B` and `DEMO_C` on the exchange `DEMO`, quoted in EUR and available.
- [ ] Feature test: the seeder creates the investment configuration and the three orders awaiting approval with the values listed under Browser tests.
- [ ] Browser test: the orders screen lists `DEMO_A`, `DEMO_B`, and `DEMO_C` in this order. In both themes, with at most 1% of the pixels differing, these elements match the mockup:
  - in `orders.html`: the page title, the Awaiting approval section heading with its count, and in the `DEMO_A` entry the symbol heading, the line with the MIC and the direction, the status badge, the trade signal details without the `asOf` note, and the order details; and the expected move "Not provided" of `DEMO_C`;
  - in `start.html`: the Orders navigation entry with the count 3, the start page's number of orders awaiting approval, and its link to the orders screen.
- [ ] Browser test, with Playwright's clock, on the orders screen scrolled down with focus on one of its elements: the time left of `DEMO_A` counts down between updates; after 30 seconds, an update runs without a page reload, the last update time changes, and the scroll position and the focus stay. The server renders the last update time to the second and Playwright's clock does not move the server's clock, so the test lets at least one second of real time pass before the update.
- [ ] Browser test, with Playwright's clock: after 30 seconds, the start page and the navigation count each run an update without a page reload.
- [ ] Browser test: while the update requests fail, the orders screen shows the lost connection message, which matches the Live updates sample of `foundations.html` in both themes. After the requests succeed again, the immediate retry runs an update at once and the message disappears.
- [ ] A manual check in the local environment is described in the PR: the demo analytics application (TM-006) publishes a trade signal for `DEMO_A`, and the logged-in operator sees the order awaiting approval on the orders screen.
- [ ] A manual check in the local environment is described in the PR: with the orders screen open and scrolled down, the order from a new trade signal appears without a page reload, stays marked for about 10 seconds, and leaves the scroll position unchanged.
- [ ] A manual check in the local environment is described in the PR: the marked order and the empty state match the Live updates and Screen states sections of `foundations.html` in both themes.
- [ ] A manual check in the local environment is described in the PR: with the start page open, a new trade signal raises the number of orders awaiting approval on the page and in the navigation without a page reload.
