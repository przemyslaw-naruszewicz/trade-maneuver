# TM-011: Orders screen

## Goal

The logged-in operator sees everything needed to decide on each order awaiting approval, and the status and execution progress of every other order. The start page and the panel navigation show how many orders await approval.

## Scope

In scope:

- A Livewire orders screen in the protected panel from TM-010, reading through the read model from TM-009, extended for the other orders ([ADR-0004](../ADR/adr-0004-livewire-eloquent-read-models.md)).
- The content of the start page from TM-010, and a count of orders awaiting approval in the panel navigation.
- Automatic updates of the orders screen, the start page, and the count, without a page reload.

Out of scope:

- Approve, refuse, and cancel actions (TM-012, TM-019), including how updates behave while their forms and confirmations are open.
- Notifications.
- Profit, performance, or effectiveness figures. The screen shows only order status and execution progress (owner decision).

## Requirements

### Orders awaiting approval

These orders are listed first, sorted by `validUntil` with the soonest first. Each shows:

- for the trade signal: instrument (symbol and MIC), direction, confidence, horizon, expected move, reference price with currency and `asOf`, `validUntil`, and the analytics application;
- for the order: order amount, limit price, quantity, and status.

### Other orders

- Each shows its status and execution progress: none, partial, or complete, with the executed quantity.
- Non-terminal orders are listed in full. Terminal orders are paginated, most recent first.
- Statuses added by later tasks (approved, submitting, open, cancelling, and the terminal ones) appear as those tasks introduce them.

### Automatic updates

- The screen updates itself every 30 seconds through Livewire polling, without a page reload. This adds no new service or dependency.
- An update replaces only what changed and keeps the scroll position and focus.
- The screen shows the time of the last successful update.
- Each order awaiting approval shows the time left until `validUntil`. The browser counts it down between updates.
- An order changed by an update stays marked for about 10 seconds.
- When updates fail, a message says that the connection is lost and that statuses and the time left may be out of date. The screen keeps trying, offers an immediate retry, and clears the message after a successful update.

### Start page and panel navigation

- The start page shows the number of orders awaiting approval with a link to the orders screen, the soonest `validUntil` with its instrument and time left, and the number of other non-terminal orders. With no order awaiting approval, it says so.
- The panel navigation shows the number of orders awaiting approval on every panel page.
- Both update themselves at the same interval as the orders screen. An update of the count leaves the rest of the page as it is, including a form being edited.

### Display

- Money and decimal values are formatted exactly, without `float`. Output is escaped.
- The component reads only through read models, never loads aggregates for display, and keeps no read model in a public property ([architecture.md](../architecture.md#cqrs), [ADR-0004](../ADR/adr-0004-livewire-eloquent-read-models.md)).

## Decisions

- The owner decided on 2026-11-03 that the orders screen updates itself without a page reload and does not disturb an operator who is deciding. The owner expects little traffic, so updates need not be frequent. The 30-second interval and the 10-second marking are proposed in this draft; the owner confirms them when approving.
- The start page and the panel navigation show and update the number of orders awaiting approval (owner decision, 2026-11-03), so the operator learns of a new order on any panel page.

## Constraints

- Keep the component thin: it handles presentation and reads through read models.
- Check the polling behavior of the installed Livewire version before relying on it.

## Acceptance criteria

- [ ] Feature test: an authenticated operator sees an order awaiting approval with every listed trade signal and order field, including the reference price `asOf`.
- [ ] Feature test: orders awaiting approval are sorted by `validUntil`, soonest first.
- [ ] Feature test: a terminal order shows its status and execution progress, and terminal orders are paginated.
- [ ] Feature test: an unauthenticated request, or one with password only, cannot see the screen.
- [ ] Feature test: decimal values are displayed exactly, using a value whose rendering through `float` would be wrong.
- [ ] Feature test: the rendered orders screen, start page, and navigation count each poll every 30 seconds.
- [ ] Feature test: the start page shows the number of orders awaiting approval, the soonest `validUntil` with its instrument, and the number of other non-terminal orders, and it says so when no order awaits approval.
- [ ] Feature test: the panel navigation shows the number of orders awaiting approval, and the next render after a new order shows the new number.
- [ ] Feature test: after an order's status or execution progress changes, the next render shows the new values and a new last update time.
- [ ] A manual check in the local environment is described in the PR: the demo analytics application (TM-006) publishes a trade signal for `DEMO_A`, and the logged-in operator sees the order awaiting approval on the orders screen.
- [ ] A manual check in the local environment is described in the PR, with the orders screen open and scrolled down:
  - the order from a new trade signal appears without a page reload, stays marked for about 10 seconds, and leaves the scroll position unchanged;
  - the time left counts down between updates;
  - stopping the `nginx` service shows the lost connection message, and starting it again clears the message.
- [ ] A manual check in the local environment is described in the PR: with the start page open, a new trade signal raises the number of orders awaiting approval on the page and in the navigation without a page reload.
- [ ] `CI_WITH_MUTATION=diff make ci` passes.
