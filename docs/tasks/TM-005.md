# TM-005: RabbitMQ transport for trade signals and signal outcomes

## Goal

Analytics applications exchange messages with Trade Maneuver through RabbitMQ:

- Trade signals are consumed from `tm.trade-signals` and acknowledged only after commit.
- Signal outcomes from the outbox are published to `tm.signal-outcomes`, into each analytics application's own queue.

## Scope

In scope:

- Adding `php-amqplib/php-amqplib`.
- A RabbitMQ service in the local Compose environment and in CI.
- The topology, the intake consumer, and the outbox dispatcher.
- Registry entries of known analytics applications, extended with outcome routing.

Out of scope:

- VPS deployment and its networks, AMQPS, connecting Proximtype, and changes in Proximtype.
- An HTTP gateway.

## Requirements

### RabbitMQ service

- Persistent storage, an explicit container memory limit, and an absolute RabbitMQ memory threshold ([ADR-0003](../ADR/adr-0003-rabbitmq-for-integration-messaging.md)).
- It publishes no host port.
- Definitions loaded at startup:
  - the `tm.trade-signals` exchange;
  - Trade Maneuver's durable intake queue, with a dead letter exchange and a dead letter queue;
  - the `tm.signal-outcomes` exchange, with one durable queue per known analytics application, routed by its identifier;
  - a Trade Maneuver user;
  - a local producer user for the demo analytics application (TM-006), allowed to write to `tm.trade-signals` and to read only its own outcome queue.
- No producer user has the `impersonator` tag.
- Credentials come from the environment. Local defaults may appear in `.env.example`, like the database password.
- Connecting another analytics application takes only configuration: a registry entry, a producer user with its permissions, and an outcome queue. It needs no change to Trade Maneuver's code.

### Intake consumer

- A long-running process, run as its own Compose service, with manual acknowledgement and a bounded prefetch.
- It passes the message body and the AMQP `user_id` to the intake use case from TM-004.
- If the use case commits, the consumer acknowledges the message.
- If the use case returns "not processable", the consumer rejects the message without requeue, so it reaches the dead letter queue.
- On an infrastructure failure, for example an unavailable database, the message is not acknowledged and RabbitMQ redelivers it.
- Graceful shutdown on SIGTERM loses no message.

### Outbox dispatcher

- A recoverable process that publishes committed outbox entries as persistent messages with publisher confirms, routed to the analytics application's outcome queue.
- The AMQP message id equals the outcome message `id`, which stays stable across retries.
- An entry is marked sent only after confirmation.
- A signal outcome that RabbitMQ cannot route (a mandatory publish that is returned) stays unsent and is logged as an error.
- Retries use backoff. A crash between commit and publication leads to publication later.

### Separation and logging

- RabbitMQ and `php-amqplib` types stay in `Infrastructure`. The application intake port takes plain inputs.
- Logs carry the trade signal `id` and the message identities.

## Decisions

- AMQP client: `php-amqplib/php-amqplib`, used directly behind the project's ports (owner decision, 2026-10-31). Approving this task approves adding the dependency. Symfony Messenger and Laravel queue drivers for RabbitMQ were rejected for now. A later switch would change only the adapters and requires an ADR.
- RabbitMQ in CI: the owner accepted adding a RabbitMQ service to CI on 2026-10-31 (SDLC §6).
- Producers identify themselves through AMQP `user_id`, as documented in [integration.md §4](../integration.md#4-transport).

## Constraints

- Verify `php-amqplib` compatibility with PHP 8.5 before relying on its APIs.
- Follow the CI change process ([SDLC §6](../../SDLC.md#changes-to-ci-configuration)):
  1. `make ci-lint`;
  2. run the affected CI variant locally;
  3. check the GitHub Actions run.
- Laravel's internal job queue stays on PostgreSQL. RabbitMQ is used only for integration messaging.

## Acceptance criteria

- [ ] Integration test against a real RabbitMQ: a message is acknowledged only after the intake transaction commits. A failure before commit leads to redelivery, and the trade signal is processed once.
- [ ] Integration test: a "not processable" message ends in the dead letter queue and is not redelivered.
- [ ] Integration test: an outbox entry is marked sent only after a publisher confirmation. After a simulated crash between commit and publication, the entry is published later with the same message id.
- [ ] Integration test: a message published as the local producer, with a contract violation, ends with `SignalRejected` in that producer's outcome queue.
- [ ] Integration test: a producer user cannot read another producer's outcome queue, and its publication with a forged `user_id` is refused by RabbitMQ.
- [ ] Integration test: the consumer stops gracefully on SIGTERM without losing an unacknowledged message.
- [ ] CI runs the RabbitMQ integration tests. `make ci-lint` and `CI_WITH_MUTATION=diff make ci` pass.
- [ ] README documents the RabbitMQ service, the consumer and dispatcher processes, and how to publish a test message locally.
