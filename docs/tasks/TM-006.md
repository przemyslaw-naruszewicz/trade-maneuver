# TM-006: Demo analytics application

## Goal

The flow can be exercised locally without Proximtype. A demo analytics application publishes trade signals that satisfy the `tm.trade-signal.v1` contract, on fictional instruments only, and reads their signal outcomes. It connects the way any analytics application does, so that connecting another one later takes only configuration on Trade Maneuver's side.

## Scope

In scope:

- A console command that publishes a trade signal through RabbitMQ.
- A console command that reads signal outcomes from the demo analytics application's own outcome queue.
- Its configuration on Trade Maneuver's side: a registry entry, plus the producer user and outcome queue from TM-005.
- The documentation listed below.

Out of scope:

- Connecting Proximtype, a separate non-public application.
- An analytical model, market data, and a scheduled stream of trade signals.
- The simulated broker in the running application (TM-008, TM-014). Until it exists, this task shows signal intake and `SignalRejected`; as later tasks add to it, the same commands exercise more of the flow.

## Requirements

### Publishing

- Each run publishes a `tm.trade-signal.v1` message as a persistent message with a publisher confirmation, and prints its `id`. A failed publication is reported as an error.
- The message carries AMQP `user_id` set to the demo analytics application's producer user ([integration.md §4](../integration.md#4-transport)).
- Its defaults produce a valid `long` trade signal for `DEMO_A`, with an invented reference price in EUR, addressed to the investment configuration named in the environment.
- Options choose the symbol, direction, confidence, horizon, expected move, reference price with its currency, signal validity, and `investmentConfigurationRef`.
- An option publishes the same message twice, to exercise duplicate delivery.
- Invalid option values are refused before anything is published.

### Fictional instruments only

- The command refuses a symbol that does not start with `DEMO_`, and it always sends the exchange `DEMO`.
- All values come from its defaults or options. It reads no market data.

### Reading signal outcomes

- The command prints each outcome message from the demo analytics application's own outcome queue (schema from TM-004), with the trade signal `id`, the outcome, and its details, and then acknowledges it.
- It says so when the queue is empty.

### Independence from Trading

- It lives outside the Trading context, in its own namespace following the same layers. It uses only the public contract: the message format, RabbitMQ, and its own credentials.
- Deptrac forbids dependencies in both directions between it and Trading.
- Trading code does not mention it. On Trade Maneuver's side, connecting it changes only configuration, which is the Open Host Service condition in [integration.md §2](../integration.md#2-ddd-relationship).
- Its registry entry and producer user exist only in the local and CI configuration.

### Documentation

- README describes its local use: creating an investment configuration that authorizes it, publishing a trade signal, and reading the signal outcome.
- [integration.md](../integration.md) gains:
  - the steps for connecting another analytics application: a registry entry, a producer user with its permissions, an outcome queue, and authorization in the investment configuration;
  - a complete example of a `tm.trade-signal.v1` message with fictional values;
  - a note that the demo analytics application has no outbox.
- The documentation describes it as simulated and fictional. It makes no promise of profit, shows no performance or effectiveness results, gives no instructions for a live brokerage account, and does not call the project production-ready or safe.

## Decisions

The owner made these decisions:

- The flow must be testable without Proximtype, through a stand-in that satisfies the contract and does not recommend real assets.
- Any analytics application that implements the contract connects through configuration alone on Trade Maneuver's side. This task set connects only the demo analytics application.
- Materials about the demo follow the documentation rules above.

Proposed in this draft; the owner confirms it when approving:

- The demo analytics application has no outbox or retries, unlike the delivery requirements in [integration.md §4](../integration.md#4-transport). It is a command run by hand, which reports a failed publication so that it can be run again.

## Constraints

- No new dependencies. It uses `php-amqplib` from TM-005.

## Acceptance criteria

- [ ] Integration test against a real RabbitMQ: a trade signal published with the command's defaults is accepted at intake and stored as coming from the demo analytics application.
- [ ] Integration test: a trade signal addressed to an unknown investment configuration ends with `SignalRejected`, and the reading command prints that outcome with the trade signal `id`.
- [ ] Integration test: publishing the same message twice creates one trade signal.
- [ ] Console command tests:
  - a symbol without the `DEMO_` prefix is refused, and nothing is published;
  - invalid option values are refused, and nothing is published;
  - a failed publication is reported as an error.
- [ ] Deptrac fails for a dependency in either direction between the demo analytics application and Trading. The PR shows the output of temporary violating classes, which are not committed.
- [ ] The PR shows that connecting it changed only configuration on Trade Maneuver's side.
- [ ] README and [integration.md](../integration.md) contain the documentation listed above and follow its rules.
- [ ] `CI_WITH_MUTATION=diff make ci` passes.
