# TM-010: Operator login with password and TOTP

## Goal

The single operator logs in to the GUI with an e-mail address, a password, and a TOTP code. A leaked password alone gives no access. Only console commands manage the operator account and TOTP.

## Scope

In scope:

- Adding `livewire/livewire` and `pragmarx/google2fa`.
- Console commands to create the operator account, reset its password, and enrol or reset TOTP.
- Login with a TOTP challenge, attempt limits, replay protection, and logout.
- A protected panel layout with a placeholder start page, for the screens in TM-011 and TM-013.
- A visible label on the login page and in the panel layout saying that the GUI works with a simulated broker.
- The GUI design system from the [mockup](../gui-design/index.html): design tokens, fonts, shared Blade components, and a light and a dark theme with a theme switch.
- Browser tests of these screens with the tooling of [SDLC-009](SDLC-009.md), with `otpauth` and a seeder for the browser-test operator account.

Out of scope:

- The SSH tunnel and VPS configuration.
- Registration, e-mail password reset, an administrator role, more than one operator, and 2FA methods other than TOTP.

## Requirements

### Accounts

- There is one operator account and no administrator role. Creating a second operator account is refused.
- The console commands are:
  - create the operator account (e-mail, and a password entered without echo);
  - reset the password;
  - enrol or reset TOTP, printing the secret and an `otpauth://` URI once.
- The TOTP secret is stored encrypted.

### Login

- Laravel session authentication with e-mail and password, without Fortify.
- After a correct password, a TOTP challenge follows. The session counts as authenticated only after a valid code.
- Attempt limits apply to the password and TOTP steps separately: at most 5 failed attempts per minute per account for each step, configurable. Failed attempts are logged without secrets.
- TOTP uses 6 digits and a 30-second step, with a tolerance of at most one step. A code that has been accepted cannot be used again (replay rejection).
- The session is regenerated on login and invalidated on logout. Every form uses CSRF protection.

### Panel and GUI

- Every panel route requires full authentication (password and TOTP). Access is denied by default.
- Livewire components are registered explicitly and stay thin ([architecture.md](../architecture.md#gui-approach)).
- No public routes exist for registration or password reset.
- The login page and the panel layout show the label "Simulated broker: no real orders". Later screens inherit it from the layout.

### Visual design

- The GUI follows the mockup in [docs/gui-design/](../gui-design/index.html). The mockup sets the look of the elements a task requires, not the task's scope. Elements that the mockup shows but this task does not require are not built.
- The panel's Tailwind theme in `resources/css/` copies the design tokens of both themes from [`tailwind.css`](../gui-design/tailwind.css), and the shared Blade components and screen states that a task requires follow [`foundations.html`](../gui-design/foundations.html). The GUI uses the mockup's fonts: Jost, IBM Plex Sans, and IBM Plex Mono.
- The application serves the font files itself, from copies in `resources/fonts/` of the files in [`docs/gui-design/fonts/`](../gui-design/fonts/fonts.css), kept with their license files, through the `local()` font provider of the installed `laravel-vite-plugin`. Neither the build nor the browser fetches fonts or other assets from an external service, so the skeleton's `bunny()` font provider, which downloads its fonts at build time, goes. `THIRD_PARTY_NOTICES.md` names where the application's font copies are.
- Application code and its build do not reference the mockup in `docs/gui-design/`: the mockup is a design source, not a part of the application. The one exception is the `@source not` line in `resources/css/app.css`, which keeps Tailwind from scanning the mockup.
- The login and TOTP pages follow [`sign-in.html`](../gui-design/sign-in.html) and [`totp-challenge.html`](../gui-design/totp-challenge.html). The panel layout and the placeholder start page follow the side panel and page frame of [`start.html`](../gui-design/start.html).
- The panel navigation starts with a Start entry, which links to the start page, and the logout action. TM-011 adds the Orders entry and TM-013 the Investment configuration entry, in the mockup's order.
- The light theme is the default. A theme switch in the panel layout changes the theme, and the browser remembers the choice, which the login and TOTP pages also apply. The choice is not stored on the server. A stored choice applies before the page is first painted, so a page never shows the other theme first.

### Browser tests

- The browser tests live in `tests/Browser/` and run with `make e2e` (SDLC-009).
- The seeder lives in `src/Trading/Infrastructure/`, because Deptrac lets the `database/` directory depend only on the composition roots and libraries. `bin/e2e` runs it with `php artisan db:seed --class=...` after migrating the e2e database. It creates the operator account with the e-mail address `operator@example.test` and a fixed password through the create-operator use case, then gives it the TOTP secret `DEMODEMODEMODEMODEMODEMODEMODEMO` through the `Operator` aggregate's TOTP enrolment, saved through the operator repository in a transaction. The tests compute TOTP codes with `otpauth` from that secret.
- The tests log in once per run, in a Playwright setup project that saves the session (`storageState`). The panel tests reuse that session. The test that logs out runs in a last project, after every other panel test, because logging out ends the session. A further login in the same run uses the code of the next time step, which the tolerance of one step accepts.
- The mockup comparisons use the helper of SDLC-009. The login page is compared with `sign-in.html` as a whole page. `totp-challenge.html` shows the error state, so the test first submits a wrong code, computed with `otpauth` to differ from the codes of the previous, current, and next time step, then types the mockup's value `480216` into the field, and compares the whole page in that state. On the start page, the tests compare the shared elements of `start.html` one by one, because the mockup shows elements of later tasks: the brand, the Start navigation entry, the theme switch, the logout action, and the page title.

## Decisions

- The owner chose Livewire for the GUI and `pragmarx/google2fa` for TOTP, without Fortify, in the working session on 2026-10-31. Approving this task approves adding both dependencies.
- Fortify was not chosen, for simplicity: the single console-managed operator needs none of its registration, password reset, recovery code, or passkey features, and it would add `bacon/bacon-qr-code` and `laravel/passkeys`. Laravel session authentication, `RateLimiter`, and `pragmarx/google2fa` cover the requirements.
- The attempt limit values (5 per minute per account and step) are proposed in this draft; the owner confirms them when approving.
- The GUI carries a visible label saying that it works with a simulated broker (owner decision). The wording is proposed in this draft; the owner confirms it when approving.
- The GUI uses Tailwind and the project's own Blade components, without a component library (owner decision, 2026-11-03).
- The owner decided on 2026-11-24 that the mockup in `docs/gui-design/` sets the look of the elements each GUI task requires, not the task's scope, and that this task adds the light and dark themes with the theme switch.
- The comparison with the mockup pages in both themes and the theme behavior are checked by this task's browser tests, not by a manual check (owner decision, 2026-11-24). They keep checking them after this task, so later changes cannot break them unnoticed. SDLC-009 delivers the tooling first, as the [definition of ready](../../SDLC.md#definition-of-ready) requires (owner decision, 2026-11-25).
- `otpauth` over a TOTP implementation of our own (owner decision, 2026-11-24): MIT, version 9.6.0 when drafted. Approving this task approves adding it as a development dependency.
- The TOTP page is compared in the error state that its mockup shows (owner decision, 2026-11-24). The application's error message is the mockup's, so the comparison also checks the look of the error state. Each wrong code counts as a failed attempt. A run submits at most two, one per theme, below the limit of 5, and each run recreates the e2e database.
- One login per run, shared through `storageState`, with the logout test last (owner decision, 2026-11-24). A TOTP code is accepted only once per 30-second step, and the seeded account is the only one, so a login in every test would be refused or would wait up to 30 seconds.
- Only the shared elements of the start page are compared (owner decision, 2026-11-24). `start.html` shows the Orders and Investment configuration entries and the execution mode of later tasks, so a whole-page or whole-panel comparison would fail.
- A spike on 2026-11-24 checked that a stored dark theme is set when the browser parses `<body>`, before the first paint, through an init script with a `MutationObserver`.

## Constraints

- Check the installed versions of Livewire and `pragmarx/google2fa` for compatibility with Laravel 13 and PHP 8.5 before relying on their APIs.
- GUI classes live in the `Ui` layer and follow the Deptrac rules.
- The change touches `bin/e2e` and `package.json`, so follow [SDLC §6](../../SDLC.md#changes-to-ci-configuration).
- Use the scratchpad or a temporary change for break checks, and do not commit them.

## Risks

- A panel test that ends the shared session early, or a test order that Playwright changes, makes the later panel tests fail. The project order keeps the logout test last.
- The browser tests compare the start page only through its shared elements and check the first paint only on the login page, so the simulated-broker band, the page frame, and the first paint of the panel are not compared with the mockup.
