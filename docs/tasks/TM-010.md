# TM-010: Operator login with password and TOTP

## Goal

The single operator logs in to the GUI with an e-mail address, a password, and a TOTP code. A leaked password alone gives no access. Only console commands manage the operator account and TOTP.

## Scope

In scope:

- Adding `livewire/livewire` and `pragmarx/google2fa`.
- Console commands to create the operator account, reset its password, and enrol or reset TOTP.
- Login with a TOTP challenge, attempt limits, replay protection, and logout.
- A protected panel layout with a placeholder start page, for the screens in TM-011 and TM-013.
- A visible label on the login page and in the panel layout saying that the GUI works with a simulated broker.

Out of scope:

- The SSH tunnel and VPS configuration.
- Registration, e-mail password reset, an administrator role, more than one operator, and 2FA methods other than TOTP.

## Requirements

### Accounts

- There is one operator account and no administrator role. Creating a second operator account is refused.
- The console commands are:
  - create the operator account (e-mail, and a password entered without echo);
  - reset the password;
  - enrol or reset TOTP, printing the secret and an `otpauth://` URI once.
- The TOTP secret is stored encrypted.

### Login

- Laravel session authentication with e-mail and password, without Fortify.
- After a correct password, a TOTP challenge follows. The session counts as authenticated only after a valid code.
- Attempt limits apply to the password and TOTP steps separately: at most 5 failed attempts per minute per account for each step, configurable. Failed attempts are logged without secrets.
- TOTP uses 6 digits and a 30-second step, with a tolerance of at most one step. A code that has been accepted cannot be used again (replay rejection).
- The session is regenerated on login and invalidated on logout. Every form uses CSRF protection.

### Panel and GUI

- Every panel route requires full authentication (password and TOTP). Access is denied by default.
- Livewire components are registered explicitly and stay thin ([architecture.md](../architecture.md#gui-approach)).
- No public routes exist for registration or password reset.
- The login page and the panel layout show the label "Simulated broker: no real orders". Later screens inherit it from the layout.

## Decisions

- The owner chose Livewire for the GUI and `pragmarx/google2fa` for TOTP, without Fortify, in the working session on 2026-10-31. Approving this task approves adding both dependencies.
- The attempt limit values (5 per minute per account and step) are proposed in this draft; the owner confirms them when approving.
- The GUI carries a visible label saying that it works with a simulated broker (owner decision). The wording is proposed in this draft; the owner confirms it when approving.
- The GUI uses Tailwind and the project's own Blade components, without a component library (owner decision, 2026-11-03).

## Constraints

- Check the installed versions of Livewire and `pragmarx/google2fa` for compatibility with Laravel 13 and PHP 8.5 before relying on their APIs.
- GUI classes live in the `Ui` layer and follow the Deptrac rules.

## Acceptance criteria

- [ ] Feature tests:
  - a correct password and code log the operator in;
  - a wrong password, or a wrong code, is refused;
  - a password-only session cannot open any panel page.
- [ ] Feature tests: the attempt limits block further attempts at each step.
- [ ] Feature tests: a replayed TOTP code is rejected.
- [ ] Feature tests:
  - an unauthenticated request is redirected to login;
  - a request without a valid CSRF token is refused;
  - logout invalidates the session.
- [ ] Console command tests:
  - the operator account is created;
  - a second account is refused;
  - a password reset changes the password;
  - TOTP enrolment prints a secret and an `otpauth://` URI and stores the secret encrypted.
- [ ] Feature test: no routes exist for registration or e-mail password reset.
- [ ] Feature test: the login page and the panel layout show the label "Simulated broker: no real orders".
- [ ] `CI_WITH_MUTATION=diff make ci` passes, and `make build` succeeds if frontend assets change.
