# TM-012A: Domain event bus for the local reactions to domain events

## Goal

Domain events reach their local reactions through `DomainEventBusInterface`, as the [architecture](../architecture.md#domain-events) describes. Command handlers and orchestrators no longer write audit records or publish integration events for domain events themselves. TM-014, TM-015, TM-017, and TM-019 add new paths that end a trade signal or change an order, and none of them can then leave out the audit record or the signal outcome message.

## Scope

In scope:

- `DomainEventBusInterface` in `Application/Port` and its adapter `LaravelDomainEventBus` in `Infrastructure/Messaging`.
- Domain event handlers for every domain event that the application records today: `TradeSignalReceived`, `TradeSignalRejected`, `TradeSignalDeclined`, `OrderCreated`, `OrderApproved`, `OrderRefused`, and `InvestmentConfigurationCreated`.
- Moving the audit records, the signal outcome messages, and the log entries of these events out of `ReceiveTradeSignalCommandHandler`, `TradeSignalEvaluationOrchestrator`, `SignalOutcomeRecordingOrchestrator`, `ApproveOrderCommandHandler`, `RefuseOrderCommandHandler`, and `CreateInvestmentConfigurationCommandHandler`.
- If TM-013 is on `main` when this task starts: domain event handlers for the domain events of investment configuration changes, and moving their audit records out of TM-013's edit command handlers.
- The location of domain event handlers in the architecture's target layout, and an architecture rule that enforces their limits.

Out of scope:

- Records of inbox facts that no aggregate records as a domain event: a duplicate delivery and the signal outcome it publishes again, a conflicting duplicate, and a message set aside. The intake handler keeps writing them.
- Workflow steps. Queuing the evaluation after a reception and queuing the signal outcome recording after a refusal stay explicit calls in the use cases, because listener chains must not define business workflows.
- Correlation and causation identifiers.
- Operator account changes, which record no domain events.
- Read model projections. Read models stay database views (ADR-0004).

## Requirements

### Bus

- A use case saves the aggregate, then dispatches the aggregate's released events through the bus, in the same transaction.
- The bus calls each handler of an event synchronously, in the order of registration. An event without a handler is dispatched without effect.
- A handler's failure propagates to the use case and rolls back its transaction, including the aggregate change.
- The adapter uses Laravel's event dispatcher with synchronous listeners only. Registration happens in the Trading service provider.

### Dispatch context

- Each dispatch carries a context with the audit actor and the extra audit values that the use case holds but the events do not: the message metadata at intake and the operator's note at refusal.
- The actors stay as they are: `analytics-application:<id>` at intake, `trade-maneuver` in evaluation and in the signal outcome recording, `operator:<id>` for approval and refusal, and the actor that the command carries for investment configuration creation and, with TM-013, its changes.

### Handlers

- A handler may write audit records, publish integration events through the outbox, and log. It must not load or change an aggregate, queue a job, or call an external system.
- `SignalOutcomeRecorder` splits into `TradeSignalRejectedSignalOutcomeHandler` and `TradeSignalDeclinedSignalOutcomeHandler` in `Application/TradeSignal/DomainEventHandler/`, one handler per event. The orchestrators no longer depend on it, and its `SignalOutcome/` directory goes away.

### Unchanged behavior

- Audit records and outbox messages keep their actors, entity types, actions, values, and order of creation, so readers of the audit trail and the analytics application see no difference.
- Log entries stay as they are, except that a rejection at intake gains the log entry that a rejection in evaluation already writes, because one handler serves both.

## Decisions

- Handlers live in `Application/{Aggregate}/DomainEventHandler/{Event}{Reaction}Handler.php`. architecture.md adds this location to the target layout.
- The context carries command data instead of the events. The events keep only domain facts, and the operator's note does not become part of `OrderRefused`.
- The task takes the suffixed ID TM-012A, so that its number lies below TM-014, which adds the next signal outcomes.
- TM-013 and this task may reach `main` in either order, and TM-013's text stays unchanged. If TM-013 comes first, this task moves its audit records into handlers (scope and AC 3). If this task comes first, TM-013 writes them in handlers, because the PHPat rules of this task require it.

## Risks

- The reactions to an event are no longer visible in the use case. The handler registry in the service provider and the handler location make them findable.
- The context can grow into a bag of unrelated values. It holds only the actor and extra audit values; correlation identifiers need their own decision.

## Acceptance criteria

- [ ] PHPUnit integration test (adapter seam): the bus calls two handlers of one event synchronously in registration order, and an event without a handler causes no error.
- [ ] PostgreSQL feature test: when a handler fails, the refusal of an order is rolled back. The order stays awaiting approval, and no audit record, outbox message, or queued job remains.
- [ ] The existing Behat scenarios and PHPUnit feature tests of audit records, outbox messages, and log entries for reception, rejection, decline, order creation, approval, refusal, investment configuration creation, and, if TM-013 is on `main`, investment configuration changes pass without changes to their assertions.
- [ ] PHPat rule: in the application layer, only domain event handlers and `ReceiveTradeSignalCommandHandler` depend on `AuditTrailInterface` and `IntegrationEventPublisherInterface`. The PR shows a break check: a command handler that records an audit record fails the rule.
- [ ] PHPUnit feature test: a rejection at intake writes the log entry "A trade signal is rejected." with the signal ID, the outcome ID, and the violations.
- [ ] PHPat rule: domain event handlers depend on no repository interface, no queue port, and no `BrokerGatewayInterface`. The PR shows a break check for each.
- [ ] Documentation: architecture.md shows `DomainEventHandler/` in the target layout, states the handlers' location, and describes the two PHPat rules of this task beside its other PHPat checks.
